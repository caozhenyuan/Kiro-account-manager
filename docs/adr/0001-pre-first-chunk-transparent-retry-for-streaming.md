# ADR 0001: 流式请求采用「首块前透明重试 + 延迟 SSE 头」而非全程缓冲或维持现状

日期: 2026-09-13
状态: 已接受（v1.7.10）

## 背景

2026-09-07 ZCode 通过反代使用 claude-opus-5 连续出现 8 次 Turn execution failed：
7 次 `fetch failed`（上游网络层瞬时错误）与 1 次 `API error 500 MODEL_TEMPORARILY_UNAVAILABLE`（上游高负载）。
当时的实现里，流式请求**完全绕过** `callWithRetry` 重试引擎——SSE 响应头（200 + text/event-stream）与
`message_start` 事件在调用上游**之前**就已写给客户端，上游一旦失败只能追加 `event: error` 收场。
客户端（ZCode）因此报 `reason=unknown retryable=false`，无法自动恢复。
非流式路径虽有重试引擎，但按错误消息文本匹配分支，`fetch failed` 不含任何状态码/关键词，零重试直抛。

## 决策

1. **延迟 SSE 头**：响应头与 `message_start`/初始 chunk 延迟到上游产出首个事件（首块）再写。
2. **首块前透明重试**：首块前失败按错误类别决策（封禁→切号；Auth→刷新 Token；配额→切号；
   过载/网络→同号退避、持续失败切号），对客户端完全不可见；重试预算与非流式共用 `maxRetries`。
3. **真实状态码收尾**：重试耗尽且首块未发出时，以真实 HTTP 状态码返回 Anthropic 格式 JSON 错误，
   而非 200 + SSE error 事件；首块已发出则维持 SSE error 事件收场（字节已送达，无法重试）。
4. **非流式补齐**：`callWithRetry` 增加网络瞬时错误与过载关键词匹配（`MODEL_TEMPORARILY_UNAVAILABLE`/high load），
   与既有 5xx 分支同策略。

## 备选方案与取舍

- **全程缓冲重试（缓冲整个响应再回放）**：可覆盖首块后失败，但流式退化为伪流式，首字延迟不可控，
  与编码 Agent 的交互体验冲突。否决。
- **维持现状，仅改非流式**：流式是 ZCode/Claude Code 类客户端的唯一路径，等于没修。否决。
- **首块前重试**（采纳）：覆盖了故障清单里的全部场景（fetch failed 与 500 高负载均发生在上游响应早期），
  保持真流式，客户端无需任何配合。

## 后果

- 首块延迟意味着客户端在上游响应前收不到字节；若上游长时间挂起，客户端需依赖自身超时
  （服务端 `requestTimeout=0` 保持不变）。未来可考虑首块看门狗（超时视为可重试失败）。
- 5xx 在账号池语义中仍为 FATAL（不惩罚账号健康度）——上游过载不是账号的错，账号切换仅由请求级重试驱动。
- 流式换号成功后，成功统计归属真正服务的账号（而非初始粘性账号）。
